# A/B Evaluation — 가설 설계 · 점수화 · 블라인드 비교

오토리서치의 모든 채택은 A/B 증거에 근거한다. 이 문서는 "측정 가능한 개선"을 만드는 방법.

## 1. 가설 설계

나쁜 가설: "코드를 더 깔끔하게 만든다." (측정 불가)
좋은 가설: "분류 함수의 정규식을 keyword set으로 바꾸면 (a) 오탐률이 내려가고 (b) 100건 처리
시간이 줄어든다." (측정 가능, 방향 명시)

가설은 항상 **무엇을 바꿔서**(개입) **어떤 지표가**(metric) **어느 방향으로**(direction)
움직이는지 담는다. 지표가 안 떠오르면 그 변경은 아직 A/B 대상이 아니다 — 먼저 측정 방법을 만든다.

## 2. 지표 카탈로그

타겟 유형별로 흔히 쓰는 객관 지표:

| 타겟 | 지표 |
|------|------|
| 코드 함수 | 테스트 통과 수, 실행시간(ms), 메모리, 오탐/미탐률 |
| 스킬 동작 | 산출물 정확도(어서션 통과율), 토큰 수, 소요시간, 단계 수 |
| 스킬 트리거링 | should-trigger/should-not 정확도(반복 측정한 트리거율) |
| 문서 | 핵심 질문 N개에 대한 답변 가능 여부, 길이 대비 정보밀도 |
| UI/앱 | 클릭 경로 완주율, 콘솔 에러 수, 렌더 시간 |

정성 항목(가독성, 유지보수성)은 수치화하지 말고 §4 블라인드 비교로 다룬다.

## 3. 정량 비교 절차

1. A안(현재)과 B안(후보)을 **동일 입력·동일 환경**에서 측정한다.
2. 가능하면 N회 반복해 평균±표준편차를 본다(특히 시간/토큰은 분산이 크다). LLM이 개입하는
   비교는 최소 3회.
3. `scripts/ab_score.py`에 두 후보의 지표를 넣어 가중 점수와 승자를 집계한다.
4. **유의미한 차이만 채택**: 차이가 측정 노이즈(반복 측정의 표준편차) 수준이면 "동률"로 본다.
   동률이면 더 단순한 쪽을 택한다.

```bash
# 예: A/B 지표 JSON을 만들어 비교
python3 autoresearch/scripts/ab_score.py compare a.json b.json
```

지표 JSON 형식은 `ab_score.py --help` 참조. higher_is_better를 지표별로 지정한다.

## 4. 블라인드 정성 비교 (서브에이전트)

가독성·설계 품질처럼 객관 지표가 없을 때:

1. A안 산출물과 B안 산출물을 준비한다.
2. 서브에이전트(general-purpose)에게 **어느 쪽이 A/B인지 알리지 않고** "출력 1 vs 출력 2 중
   어느 쪽이 더 나은지 이유와 함께"를 묻는다. 순서는 무작위화한다.
3. 판정과 근거를 원장에 기록한다. 판단이 갈리면 두 번째 판정자를 둔다.

자기가 만든 B안을 자기가 평가하면 편향된다 — 독립 판정자를 쓰는 이유다.

## 5. 스킬 동작의 A/B (with-skill vs baseline)

스킬 자체를 개선할 때는 skill-creator 방식의 대조를 차용한다:

- **A(baseline)**: 기존 스킬 버전 스냅샷.
- **B(candidate)**: 개선 버전.
- 같은 테스트 프롬프트를 두 서브에이전트에 각각 주고(한쪽은 A 경로, 한쪽은 B 경로) 산출물·토큰·
  시간을 비교한다.
- 2~3개의 현실적인 테스트 프롬프트를 쓴다. `evals/` 디렉터리에 누적하면 다음 사이클에서 재사용.

## 6. 채택 체크리스트

채택(커밋) 전 모두 ✓ 여야 한다:

- [ ] 가설이 측정 가능한 형태로 원장에 기록됐다
- [ ] A·B를 동일 조건에서 측정했다
- [ ] B의 우위가 노이즈 수준을 넘는다 (또는 동률+더 단순)
- [ ] VERIFY 단계에서 회귀가 없음을 확인했다
- [ ] 폐기한 경우에도 학습을 `discarded_hypotheses`에 남겼다
